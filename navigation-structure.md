# Secure-by-Design Handbook – Navigation Structure

Information architecture, URL conventions, and routing for `https://www.securebydesignhandbook.com`, aligned with `docusaurus.config.ts`, `sidebars.ts`, and `docs/`. Which pages are entry points from search, and the job each overlapping page owns, are set in [entry-page-seo-strategy.md](./entry-page-seo-strategy.md).

**Aim**: a clear, role-oriented path from the homepage to implementation material.

## Top-Level Navigation and Sidebars

The navbar holds the five handbook sections, then GitHub, the theme toggle, and search. The logo and **Secure-by-Design** title link to `/`.

1. **Quick Start** (`quickStartSidebar`, `docs/quick-start/`)
2. **Standards** (`standardsSidebar`, `docs/standards/`)
3. **Implementation** (`implementationSidebar`, `docs/implementation/`)
4. **Resources** (`resourcesSidebar`, `docs/resources/`)
5. **Tools** (`toolsSidebar`, `docs/tools/`)
6. **GitHub**

Each sidebar is autogenerated from its folder. Order pages with `sidebar_position` in front matter and groups with `position` in each folder's `_category_.json`; set `sidebar_label` where the page title is too long for the sidebar.

Organize top-level navigation around reader jobs; do not add a navbar item for a single regulation, standards body, or vendor.

The **blog** (`/blog/`, scope in [purpose-and-positioning.md](./purpose-and-positioning.md#news)) is not in the navbar, so the navbar keeps the five handbook sections on one line. Readers reach it from the homepage's Stay updated section and the footer's Community column. Site search indexes doc pages only, because posts are dated snapshots.

## URL and Linking Conventions

Docs are served under `/docs/`:

- Canonical domain: `https://www.securebydesignhandbook.com` (the bare domain redirects to it)
- `baseUrl`: `/`
- Docs route: `/docs/` (Docusaurus default)
- Blog route: `/blog/`
- `trailingSlash`: `false` – keep it, to avoid canonical URL churn

URL convention:

- **From the file path**: a page's URL comes from its path under `docs/`, so name files with lowercase letters, digits, and single hyphens, using the key words of the page title (`secure-boot.md`, `cra-gap-analysis.md`).
- **`slug` front matter**: only to keep a published URL stable when its file moves. Two exist and must stay: `/docs/standards` (the Standards overview) and `/docs/standards/eu/cra-overview` (the CRA overview, a preserved entry URL).
- **Blog posts**: name files `blog/YYYY-MM-DD-short-slug.md`, dated to the event the post reports. Docusaurus serves them at `/blog/YYYY/MM/DD/short-slug`.
- **URL stability**: the site is public and indexed. Change a published URL only with a redirect from the old one, or keep the old URL with `slug`.

Linking guidance:

- **Between docs**, use relative Markdown file paths, with the anchor where needed, so links survive a change to the URL structure and the build checks them:
  - Good: `[CRA Overview](../standards/eu/cra/index.md)` and `[harmonised standards](../standards/eu/cra/index.md#harmonised-standards)`
  - Bad: `[CRA Overview](/docs/standards/eu/cra-overview)`
- **In `docusaurus.config.ts` and React pages** (`src/pages/`), use canonical paths without a trailing slash (`/docs/implementation/build-phase/secure-boot`).
- **In blog posts**, link handbook pages with canonical paths (`/docs/standards/eu/cra-overview`), inline where each helps the reader.
- Broken links fail `npm run build`; broken Markdown links only warn, so check them before merging.

| :--- | :--- |
| **Compliance lead** | Quick Start → CRA primer → CRA gap analysis → CRA overview → Secure-by-Design evidence pack |
| **Firmware engineer** | Implementation → Build phase → Unique device identity → Secure boot → Key provisioning |

## Homepage and Footer Routing

- **Homepage (`src/pages/index.tsx`)**: a Deep Teal hero with the site title, tagline, and two buttons (What is Secure-by-Design? and the Implementation overview); three pillars under *Turn regulatory requirements into engineering reality*; four cards under *Choose your next step* (Understand obligations → CRA primer, Assess readiness → CRA gap analysis, Implement controls → Implementation, Assemble evidence → evidence pack); three cards under *Get started by role*; and a closing section with GitHub and Contribute links and a Stay updated link to the blog.
- **Footer (`docusaurus.config.ts`)**: three columns – **Quick Start**, **Implementation**, and **Community** (Latest News, Contribute, Glossary) – above one copyright line naming the Secure-by-Design Handbook contributors and the CC BY-SA 4.0 license. Keep footer labels short so the columns fit on mobile.

## Section Placement and Expansion Rules

Add a page only when there is enough distinct, decision-useful material that an existing page cannot hold cleanly, and place it by reader job:

- **A regulation, standard, or official guidance document** goes under `/docs/standards/<region>/`, where `<region>` is `eu`, `uk`, `us`, `australia`, or `global`. A regulation with several related pages gets its own folder (as `eu/cra/` does), and CRA harmonised standards follow the page structure in the style guide.
- **How to build a control into a product** goes under `/docs/implementation/build-phase/`; **how to run it after release** goes under `/docs/implementation/operate-phase/`. Keep the build phase in workflow order.
- **Something a reader fills in, follows, or looks up** goes under `/docs/resources/`, in the group named for what they do with it (checklists, policy and evidence, examples, case studies, hardware, cryptography, reference). Definitions go in the glossary.
- **A tool landscape for a security task** goes under `/docs/tools/`, in workflow order, listing several options rather than one vendor.
- **A dated development** goes in a blog post, together with any change it makes to a handbook page. Handbook pages may link to the blog listing, never rely on a post as the only source of a fact.
- **Overlapping topics**: before adding a page that overlaps an existing one, check the cross-page routing rules in [entry-page-seo-strategy.md](./entry-page-seo-strategy.md) and give each page a separate job.
